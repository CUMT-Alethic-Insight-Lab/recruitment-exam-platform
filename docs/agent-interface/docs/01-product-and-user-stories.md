# 01 · 产品定位、边界与用户场景

## 目标

减少成员获取组织信息、办理事务、填表、申请与查询进度的非生产性时间，而非代替科研、写代码、实施管理决策。尊重人已有工具习惯、兴趣、选择权和发声权；让成员通过相同的授权业务能力获得同等机会。

### 北极星指标（建议，不是现成数据）
- 组织事务**首次成功完成率**：成员不寻求负责人私聊即可成功提交/查询。
- **中位完成耗时**：查一项信息、提交一份申请和获取状态所需时长。
- **可追溯性**：每条答复引用权威信息或标注缺失；每次写入可定位操作者及审批人。
- **渠道一致性**：网页、REST、CLI、MCP 对同一业务返回一致的字段、权限和状态。
- **成员控制感**：用户能预览、撤销未处理草稿、撤销客户端授权、导出自己可访问的信息。

## 角色与权限不是同一维度

- 普通成员：有权查看成员级制度、自己的申请及允许查看的项目。
- 项目成员/负责人：仅获得参与项目内特定资源的权限；与组织管理角色正交。
- 资源管理员/审批人：可以处理被分配的申请；不能因此读取全体私密资料。
- 组织管理员：负责成员资格、规则与授权管理；敏感操作另需审批或至少强确认。
- 未认证访客：只能访问独立公开的网站/仓库；**不得访问内部 API 资源**。
- 个人 Agent：**不拥有独立的成员身份**，仅代表成员在明确授权的范围内调用工具。

## MVP 的四类场景（必须跑通）

| 场景 | 会员问题 | 最小后端支持 | 不允许发生 |
|---|---|---|---|
| 组织信息 | 我该怎么加入这个项目？ | 搜索/读取已授权的文档、返回来源 | 臆造规定或泄露内部文件 |
| 表单草稿 | 帮我整理设备借用信息 | 表单 schema、草稿字段、缺失项 | 偷偷提交、编造库存 |
| 提交申请 | 申请参与某个项目 | 提交、确认、幂等、审批状态 | Agent 直接批准或自动调人 |
| 进度查询 | 我上周的申请怎么样了？ | 按主体查询本人申请 | 通过 ID 枚举看他人申请 |

### 端到端用户故事 A：查询

作为成员，我希望从个人 Coding Agent 问“目前哪些项目开放报名”，Agent 调用组织 CLI 查询，把项目名称/开放状态/入口/更新时间反馈给我；如果当前状态未知，清楚表明未知而不是猜测。

### B：表单办理

作为成员，我说“申请视觉项目借一块开发板，打算下周用一周”。CLI 或 Agent 读取表单结构，填入明确提供的字段；缺少具体设备、日期、归还人时提问。提交前显示规范化预览，**用户同意**后才调用写 API，得到申请编号及状态。

### C：负责人处理

审批人进入网页后台，查看分配给自己的申请并决定批准/拒绝/要求补充；每次决定要求记录负责人、时间与必要理由。Agent 可以替用户准备文本，但不改变审批责任。

### D：退化模式

当个人 Agent/DeepSeek 不可用，成员仍然通过 `alethic` CLI 或网页提交申请；当 GitHub 暂时故障，组织事务系统可以显示最后同步时间并允许与 GitHub 无关的申请流转。

## MVP 暂不支持

全文搜索所有仓库、全员跨项目匹配、成员能力画像/评分、自动项目调度、训练流程、论文推荐、自主连续循环 Agent、自动 Slack/QQ 群抓取、费用分配商城。后续必要时单独进行隐私/管理评估。

## 关键用户体验规则

1. 任何路径都能找到“我在哪里看这个规定”和“谁能处理这个申请”。
2. 一次申请中不要让用户重复填写平台已确认且当前有权限使用的信息；允许人工覆盖。
3. 平台只要求提交**业务必要**的个人信息；不以公开心理、生活或成绩隐私交换项目机会。
4. 成员的选择权不是无限写权限；不同入口执行同一授权规则。
5. 有争议的组织规则一律链接到正式文件，并呈现版本与生效时间；不能依模型自己判断替换正式制度。
