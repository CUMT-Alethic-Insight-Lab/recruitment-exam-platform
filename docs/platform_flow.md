# Alethic Insight 招新平台 — 流程与接口形态梳理（粗粒度）

> 定位：本文档只做流程与接口形态的顶层设计，供后续交代 coding agent 逐模块实现。不锁定技术栈，只锁定数据流与契约。

## 0. 核心设计原则

- **学号为主键**：问卷、机试会话、K3 打分、面试打分，全链路用 `student_id` 串联。
- **一次开发，长期复用**：每届招新 = 新建一个 `campaign`（招新批次），所有数据挂在批次下。
- **数据生命周期 30 天**：云端下发的机器标识号与考生数据自创建起 30 天超时自动回收——回收标识号并删除该批次所有原始数据（评审结论与录取名单另行归档留存）。招新数据不留存是隐私设计，不是缺陷。
- **模型接入开放**：机试不绑定特定模型。默认用 opencode 自带的免费模型；允许考生接入自己的大模型 API。考试机不固定（机房/自带设备均可）。题目性质决定答案无处可查，考生之间的沟通不阻止也不鼓励——是否有定势思维（照搬/跟风）本身是会话中的观察点。
- **降级兼容**：机试可整体跳过（`exam_status = waived`），流程不断链。
- **数据可导出**：30 天回收窗口内，管理端任何时候能导出全量 CSV/JSON。

## 2. 模块划分与接口形态

### M1 问卷模块（云端 Web 表单）

- **形态**：单页表单，无需注册，提交即建档。
- **字段**（对应已定稿的问卷）：
  - `student_id`（学号，主键，格式校验）/ `name` / `gender` / `class_name` / `qq`
  - `lab_intent`（是否有意向加入实验室，bool）—— False 即走社团通道，不进后续流水线
  - `domains`（领域多选，≤3，枚举见附录 A）
  - `focus_next_year`（绩点学业 / 学生工作 / 科研 / 项目经验，单选，仅作常驻概率画像，不作硬筛选）
  - `expectation`（期望收获，开放文本）
- **接口**：`POST /api/campaigns/{cid}/applications`；管理端 `GET` 列表 + CSV 导出。
- **备注**：提交后返回确认页（含机试时间地点通知文案）。
- **现场补录口子**：机试现场允许未填问卷者先考——学号登录时若云端无问卷记录，登录界面直接内嵌精简版问卷（必填字段同上，开放题可答「现场补录」），提交即建档、即时下发题目。问卷系统与题目下发系统共用同一存储，**全程以学号为唯一标识符做数据对齐**，不设考号等任何第二标识。
- 数据对齐规则：所有模块（问卷/会话/评分/面试）写入前必须先按学号 resolve 到 Application 记录；学号不存在时拒绝写入并提示先建档，杜绝孤儿数据。

### M2 机试平台安装包（考试机本地，双击即用）

- **交付物**：一个安装包，内含启动器 `AlethicInsight社团招新机试平台.ps1`（或打包成 `.exe`）。不预配任何模型 API key——opencode 自带免费模型开箱可用，考生也可自行接入自己的 API。
- **启动流程**：双击启动器后拉起两个进程：
  1. **opencode web**：作答环境本体
  2. **清洗上传 web 界面**：学号登录入口 + 题目展示 + 考试结束后的一键清洗上传
- **学号登录与题目下发**：考生登录入口输入学号 → 云端校验该学号在当前批次的状态：
  - 已有问卷记录 → **直接下发该生的题目**（按问卷所选领域配题，配题规则见题库文档附一）
  - 无问卷记录 → 弹出内嵌精简问卷（现场补录口子），提交建档后立即下发
  - 已有机试会话 → 拒绝重复开考（或按监考授权的「重考」流程作废旧会话后重发）
  - 下发同时返回本次会话凭证 `session_token`。
  - 这一设计同时解决两件事：**上传鉴权**（后续上传只认 session_token，无线下发 token 的必要）与**题目保密**（题目不进安装包、不提前落地，开考登录才可见）。
- **机器标识**：`machine_id` 不由本地写入，而是登录时**云端下发**（ alethicinsight.com ），与会话绑定；**30 天超时自动回收标识号并删除关联数据**。
- **自检**：启动器拉起后自检两项——opencode web 可访问、云端连通，输出 OK/FAIL。

### M3 会话清洗 / 上传（清洗上传 web 界面内）

- **触发**：考试结束，考生在清洗上传界面点击「结束并上传」。
- **清洗规则**：基于 opencode 会话的本地存储结构（具体仓库位置与会话导出结构以实现时实际勘察为准），用可配置的正则/结构规则提取以下事件流：
  - **用户 prompt**（原文）
  - **模型正式回复**（不含思考链）
  - **模型工具调用行为**（工具名、参数摘要、执行结果退出码/输出摘要）
  - **文件 diff**
  - **git commit 链**（若有提交行为，保留 commit message 与顺序）
  - **会话元事件**：上下文压缩事件、用户手动中断/回退事件（这些是判断考生掌控力的重要信号，必须保留并标注）
- **打包上传**：清洗后 JSON（含 student_id / machine_id / session_token / 时间戳）上传云端；原始会话本地保留一份备份。
- **接口**：`POST /api/campaigns/{cid}/sessions`（鉴权 = 登录时下发的 `session_token`，一证一传，防重复防伪造）。
- **兜底**：上传失败则留在本地 `pending_upload/` 并在界面醒目提示，监考可手动重传。
- **清洗规格**：与评审方案文档对齐，清洗规则做成可配置的 filter 列表，方便随 opencode 版本升级迭代。

### M4 K3 评审模块（云端，半自动）

- **形态**：管理后台一个「评审」页 + 一个批处理脚本。
- **流程**：拉取本会话清洗文本 → 拼入打分 prompt（维度 rubric 见评审方案文档）→ 调 K3 → 解析结构化输出回写。
- **数据结构**：
  ```
  exam_score: { student_id, campaign_id, dimensions: [{name, score(1-5), comment}],
                overall_grade(A/B/C/D), summary, reviewed_by: "k3", human_override: {...}? }
  ```
- **接口**：`POST /api/campaigns/{cid}/sessions/{sid}/score`（触发评分）；`PATCH` 人工覆写。
- **人工复核入口**：K3 打完分后，你能在列表页按总分排序浏览，点进去看原文+分数，必要时改分。

### M5 面试打分模块（云端 Web 表单）

- **形态**：面试官视角的打分页，按学号搜索调出考生卡片：
  - 考生卡片 = 问卷信息 + 机试分数 + 机试会话摘要（K3 生成的 summary）
  - 打分表 = 技术维度 + 人品维度（见评审方案），每项 1~5 + 备注
  - 底部：录取建议（强烈推荐 / 推荐 / 待定 / 不推荐）
- **接口**：`POST /api/campaigns/{cid}/interviews`；列表页 `GET` 按面试综合评级排序。
- **决策模型**：机试=摸底（分数仅用于预选圈定与面试追问材料），面试=门槛（录取裁决依据，印象+量化）。机试分数不进最终计算，平台不需要加权公式，只需支持按机试分排序（预选用）和按面试评级排序（收录用）两个视图。

### M6 名单与收口

- 预选名单：机试分数排序取前 ~20 + 人工微调，状态机：`applied → tested → shortlisted → interviewed → admitted/rejected`
- 最终名单导出：CSV + 一页公示文案模板
- 社团通道（`lab_intent=false`）：单独列表，一键导出 QQ 号用于拉群，不走评分。

## 3. 数据模型（最简）

```
Campaign(id, name, year, status, expires_at)   -- expires_at = created_at + 30d
Application(student_id PK, campaign_id, name, gender, class_name, qq,
            lab_intent, domains[], focus_next_year, expectation, created_at)
ExamSession(id, campaign_id, student_id FK, session_token, machine_id(云端下发),
            domain_tags[], questions_served[], cleaned_file_path, status, uploaded_at)
ExamScore(session_id FK, dimensions[], overall_grade, summary, human_override)
Interview(id, campaign_id, student_id FK, tech_scores[], persona_scores[],
          recommendation, notes, interviewer, created_at)
-- 定时任务:expires_at 到期 → 回收 machine_id、删除该 campaign 全部原始数据
-- （问卷/会话/评分原文）,仅保留脱敏的录取结论归档
```

## 4. 非功能性要求

- **隐私**：问卷与会话含个人信息，云端库不公开；**全部原始数据 30 天自动回收删除**（见 §0 数据生命周期），评审期必须在此窗口内完成；GitHub 公开仓库（join-us）按章程**绝不**放真题、评分标准、候选人评价——平台代码里的 rubric/prompt 与题库视为敏感材料，放私有仓库；题目只在开考登录后由云端下发，不进安装包。
- **考试行为边界（写进考场须知）**：允许使用任意 AI 工具（自带 API 亦可）、不阻止考生间沟通也不鼓励、允许查任何资料——题目性质决定答案无处可查；照搬他人思路而不自洽者会在面试追问中暴露。
- **兜底**：每个环节都有本地降级（问卷挂了用纸质表、上传挂了留本地、K3 挂了人工看原文）。
- **规模假设**：单届报名 ≤300，机试 ≤150 人一场，面试 ≤30 人——任何轻量栈（SQLite + 单容器都够）都能扛。

## 附录 B：机试轨迹与评分要点（2026-03 修订）

- 机试分三条轨迹：`track1` 研发型（理论/概念导向，按领域下发题库题）、`track2` 实操型（落地实践，按领域下发题库题）、`track3` 自由创作型（不依赖题库，自选领域现场创作或对已有项目做增量，导出 mini-session 作为轨迹依据）。
- 不限时长；考生可临时换题（`reroll_limit` 默认 2 次，配置在 campaign `exam_config`）。
- 评分标准：看**增量**（相较既有基础的实质新增）+ **人类率**（相对 AI 率，人机混合中的人类贡献）。

## 建议开发顺序（交代 coding agent 时）

1. M1 问卷（定死 student_id 主键与枚举，是上游；登录校验依赖问卷记录）
2. 云端登录/下发题目/session_token 接口 + M2 安装包启动器（双进程拉起 + 学号登录）
3. M3 清洗上传（先勘察 opencode 会话存储结构，再定正则规则；机试前必须 ready）
4. M4 K3 评审（机试后、面试前 ready 即可）
5. M5 面试打分（面试前 ready）
6. M6 收口 + 30 天自动回收定时任务（最后）
